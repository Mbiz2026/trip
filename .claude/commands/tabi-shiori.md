# 旅のしおり自動生成

## 発動条件

次のいずれかで発動する。**ユーザーが条件を言わなくても、下記「毎回守る5条件」は常に適用される。**

- `/tabi-shiori` が明示的に呼ばれた
- **航空券・ホテル・ツアーの予約画面のスクリーンショットが貼られた**(言葉が「これになったから作って」だけでも、あるいは無言でも発動する)
- 行き先と日程が示されて「しおり」「旅程表」「旅のしおり」が求められた

予約スクショが貼られたら、まず読み取った内容(便名・区間・日時・金額・予約番号・予約の分割)を箇条書きで復唱し、**それが合っているかだけを確認してから**調査に入る。行き先・日程が読み取れない場合のみ聞き返す。

---

## 毎回守る5条件(ユーザーの原文・要約せずそのまま適用)

1. **前回作ったしおりの最終版に盛り込んだ情報を全て網羅すること**
   → 直近の `travel_tools/shiori_*.html` のタブ構成と項目を読み、**取りこぼしをゼロにする**。減らすなら理由を述べて事前に確認する。
2. **全ての情報は細部まで確実なソースを元に記載すること**
   → 一次情報(政府・大使館・航空会社・空港・施設の公式)を優先。二次情報は「二次情報」と明記する。
3. **再確認を徹底し、1行たりとも誤りがないことを数回にわたって裏を取ってから確定情報として盛り込むこと**
   → **1ソースで確定にしない。** 特に時刻・金額・営業時間・法規は2ソース以上で突合する。
4. **旅行中にも質問が飛んでくる。盛り込んだ情報はすぐ出せるよう明確なソースを元にストックしておくこと**
   → しおり本体とは別に **`travel_tools/notes/shiori_<地名>_<YYYYMMDD>_sources.md`** を必ず作る。旅行中の質問はまずここを読む。
5. **友人にも共有する。納品は「共有可能なURL」のみ**
   → **ファイルは渡さない。Artifactも使わない。** GitHub PagesのURL1本だけを出す。そのURLは**ホーム画面に追加でき、Service Workerでオフラインでも開ける**こと。実際にURLを開いて確認してから渡す。

### 修正依頼を受けたときの追加ルール

- **指定された箇所以外は一切変えない。**
- 指定外に書き換えが必要だと判断した箇所があれば、**実行前に全てユーザーに確認を取る**(勝手に直さない)。
- 修正版も共有できる形式で出力し直す。

## 成果物は3点セット

| # | 成果物 | パス |
|---|---|---|
| 1 | しおり本体(1ファイル・オフライン動作・PWA) | `travel_tools/shiori_<ローマ字地名>_<出発日YYYYMMDD>.html` |
| 2 | **調査ノート**(旅行中Q&Aの根拠) | `travel_tools/notes/shiori_<同名>_sources.md` |
| 3 | **共有URL(GitHub Pages)— これが唯一の納品物** | `/shiori.html`(共有用)と `/shiori-<YYYYMMDD>.html`(保存用) |

3つ揃って初めて納品。`.github/workflows/pages.yml` の paths と dist コピー処理に新しいファイルを追加する。

## 手順

### 0. 予約情報の読み取りと復唱
スクショから便名・区間・定刻・機材・ターミナル・予約番号・金額を書き出す。**予約が複数に分かれている場合は分けて管理する**(例: 予約A=往路のみ、予約B=以降3便)。荷物の通し可否・乗継の扱いが予約の境界で変わるため、ここを曖昧にしない。

### 1. 便の裏どり(最重要・ここで手を抜くと全部崩れる)

各便について **4点を必ず実データで確認**する。
**(1)便名 (2)出発時刻と到着時刻 (3)到着が当日か翌日か (4)運航曜日**

**公開時刻表と運航実績の2ソースで突合する:**
- 公開時刻表: `info.flightmapper.net`
- 運航実績: `www.planemapper.com`(直近7日程度の実際の発着を見る)

食い違ったら**実績側と予約画面を優先**し、ノートに食い違いを記録する。

> 実例: VN320 は FlightMapper が「00:20発」を持っていたが、PlaneMapper の直近7日の実績は全て「00:10発」。予約画面も00:10。→ 00:10が正。

所要時間や相場といった**間接的な数字から到着日を逆算するのは禁止**。過去に「所要11時間40分」から到着日を計算して行程表を書き、ユーザーに指摘された実績がある。

### 2. 調査(各項目に出典URLと確認日を控える)

- **入国要件**: ビザ/電子ビザ/電子入国申告の要否、**政府公式の申請URLのみ**。印刷の必要部数まで確認する(カンボジアe-Visaは**2部**必須・画面提示は不可だった)
- **外務省 海外安全ホームページ**: 危険情報・スポット情報・安全対策基礎データ。**レベルは地域ごとに分かれる**ので、訪問都市が何レベルかを特定する。楽観的に言い換えない
- **パスポート残存期間**: 各国の要件を調べ、**「最終入国日」起点**で必要な有効期限を計算する(出発日起点で計算して誤った実績あり)
- 気候・服装、**日の出/日の入り**(§落とし穴参照)
- 空港→市内の移動手段と料金相場、交通アプリ
- 通貨・両替・チップ・カード事情・偽札情報
- eSIM・通信
- 祝日・イベント・休業日
- 定番の詐欺・ぼったくり手口
- **電源(電圧・プラグ形状)、モバイルバッテリーの機内規制**
- **手荷物規定**(航空会社別・預け/持込の重量とサイズ)
- **ラウンジ**(Priority Pass 公式で全空港分。航空会社系の離脱に注意)
- **医療・健康**(感染症、予防接種、医療水準、キャッシュレス保険の要否)
- **緊急連絡先**(大使館・警察・救急)

### 3. 生成

- デザイントークン(色・フォント・タブ構成)は `travel_tools/kaigai_travel_kit.html` と既存しおりから流用し、姉妹アプリに見えるようにする
- **外部リソース禁止**(CDN・画像URL・Webフォント)。1ファイル完結・オフライン動作
- **CSSだけでタブが動く構造**(`.tabradio` ラジオ + `:checked` + `~`)。JavaScriptは計算機・検索・チェック保存のみ
- **PWA**: manifest・アイコンは**しおり固有の名前と `start_url` が必要なのでbase64 data URIで`<head>`に埋め込む**。加えて **Service Workerを登録する**(共有の `travel_tools/pwa/sw.js` を使う。Pages配信時に `shiori.html` と同じ階層に置かれる)
  ```html
  <script>
  // オフライン動作用。https のときだけ登録する(ローカルファイルで開かれたとき例外を出さないため)
  if ('serviceWorker' in navigator && location.protocol === 'https:') {
    addEventListener('load', () => navigator.serviceWorker.register('./sw.js').catch(() => {}));
  }
  </script>
  ```
  **納品がURLのみになったため、オフラインの保証はService Workerが負う。** 圏外・機内で開けないしおりは納品不可
- ヘッダーに **情報確認日**(更新したら「(○○は△月△日に更新)」を追記)、フッターに免責
- 不確かな情報は `<span class="badge warn">要確認</span>` / `二次情報` と明記し、**行程を左右する判断には使わない**
- **最後のタブは必ず「出典と確認日」**。旅行中の質問の回答根拠になる

### 4. 検証(納品前に必ず通す)

**まず静的検査を走らせる(毎回手で書き直さない):**
```
python3 travel_tools/dev/verify_shiori.py travel_tools/shiori_<...>.html
```
外部リソース0件 / タブのラジオ・ラベル・パネルの三点一致 / JSで初期表示を作る空要素 / selectのoption / タグの対応 / 情報確認日・免責・出典タブ / PWAのmanifestとアイコン を一度に検査する。**全項目OKになってからブラウザ確認に進む。**

次にPlaywrightで `executable_path='/opt/pw-browsers/chromium'`、`viewport=390x844`:
- `java_script_enabled=False` で**JS無し**の表示とタブ切り替え
- `color_scheme='dark'` と light の**両テーマ**
- 機械チェック: **タブ数 == ラジオ数 == ラベル数** / **外部参照0件** / タグの対応 / 横スクロールなし

直接起動(`--screenshot`)は幅が最小500pxに切り上げられ右端が切れて写る。`--blink-settings=scriptEnabled=false` はこの環境で無出力に失敗する実績あり。**Playwrightを使う。**

### 5. 配信(納品物はURL1本だけ)

**納品は共有URLのみ。HTMLファイルを渡さない。Artifactも使わない。**

`https://mbiz2026.github.io/trip/shiori.html`(共有用) / `/shiori-<YYYYMMDD>.html`(保存用)

手順:
- `.github/workflows/pages.yml` の `paths` と dist コピー処理に新ファイルを追加
- **`travel_tools/pwa/sw.js` の `VERSION` を上げる**(利用者のキャッシュを確実に更新。本体を更新したら必ず)
- **デプロイは `main` からのみ成功する**(`github-pages` 環境の保護ルール。作業ブランチからの実行は約1秒で失敗する)→ PRを作ってmainにマージする

公開後、**URLを実際に取得して次を確認してから報告する:**
- HTTP 200 で、中身がテスト済みのファイルと一致する
- `sw.js` と `manifest` が同じ階層から 200 で取れる
- **Service Workerの登録コードが本文に含まれている**(オフライン動作の前提)

### 6. 報告

**要点3行 + 共有URL1本 + 「ホーム画面に追加」手順**だけを渡す。ファイルのパスや添付は出さない。

友人へ転送する用の案内文も添える:
> このURLを開いて、Safariの共有ボタン→「ホーム画面に追加」。アプリとして開けて、一度開けば電波が無くても見られます。

(**一度Safariのタブで開いてから追加**するよう必ず書く。プレビューから追加すると正しく動かないことがある)

**ユーザーはコードを書けない。専門用語を使わず、やったことと使い方だけを平易な日本語で伝える。**

## タブ構成のテンプレート(前回の最終版 = 網羅すべき下限)

1. **行程と関門** — 便ごとの時刻表、乗継時間、各空港での関門(入国審査・荷物・保安)
2. **事前手続き** — ビザ/e-Visa/電子入国申告、公式URL、印刷部数、パスポート残存期間
3. **現地の目玉**(遺跡・観光) — 開門時刻、料金、服装規定、チケット購入場所
4. **持ち物** — 印刷物の部数まで具体的に
5. **薬と健康** — 感染症、予防接種、医療水準、保険
6. **電源と機内** — 電圧・プラグ、モバイルバッテリー規制、手荷物規定
7. **お金と通信** — 通貨、両替、カード、偽札、eSIM
8. **ラウンジ** — 全空港分、場所・営業時間・利用条件
9. **注意と緊急** — 外務省の危険情報、詐欺手口、大使館・警察・救急
10. **出典と確認日** — 全項目の出典URLと確認日

行き先に応じて増やすのは良い。**減らすときは理由を述べて事前確認。**

## 調査ノートに必ず入れる章

本体に載せきれない一次情報の控え。**旅行中に質問が来たらまずこれを読む。**

1. 予約便(実データで裏どりした表+食い違いの記録+裏どり手順)
2. 外務省 危険情報(引用・発出日・地域別レベル)
3. 入国要件(国別)
4. 医療・健康
5. 緊急連絡先
6. ラウンジ(空港・施設・場所・営業時間・条件)
7. 手荷物(航空会社別)
8. モバイルバッテリー等の規制
9. 現地情報(遺跡の開門・料金・服装・交通相場)
10. その他(電源・通貨・気候・時差・連休)
11. **喫煙所**(全空港+ホテル+主要施設。法規と罰金、電子タバコの合法性を国別に)

### 旅行中に実際に聞かれた項目 — 次回は先に仕込む

今回の旅で質問が飛んできて、ノートに無くて調べ直した項目。**最初から入れておく。**

- **喫煙所**(空港は制限エリア内/外を分けて。ホテル、モール)
- **電子タバコの合法性**(タイは違法・所持で拘束事例/ベトナムは2025年から全面禁止/国別に必ず調べる)
- **空港のターミナル構成**(T1/T2が存在するのか。チェックインの列/Row。Grab等の降車地点と階)
- **荷物のスルー可否**(航空会社の公式規定+現場での判別方法)
- **ローカルフード**(名前・何か・相場。**朝しか売っていないもの**を区別する)
- **土産の名産品**(何が特別なのか、偽物の見分け方、相場、買い方)
- **現地の天気の実データ取得方法**(`curl -s "https://wttr.in/<都市>?format=j1"` で時間別の雲量・降水確率が取れる)
- **観光地の服装規定と開門/閉門時刻**

## 既知の落とし穴(すべて実際にやらかした記録)

### 情報の正しさ
- **時刻表サイトは古い値を持つ** → 運航実績と突合(VN320: 00:20 vs 実績00:10)
- **運航曜日の検索結果が誤っていることがある** → 実際の曜日の運航履歴で確認(VJ939/VJ903の水曜運航を誤判定した)
- **二次情報の営業時間は信用しない** → Foursquare/Tripadvisorが「22:00閉店」としていた店が**実際は21:00閉店**でユーザーを空振りさせた。営業時間は**公式サイトか電話**で裏を取り、取れないなら「二次情報・要確認」と明示して代替案を同時に出す
- **日の出/日の入りは検索結果を信じない** → NOAAの太陽位置アルゴリズムで計算し、gaisma.com の実測値と突合(検索結果の06:23はgaismaの「-6ヶ月」行だった。正解は05:54)
- **外務省の記述を一般化しない** → 「3カ国とも監禁事案」と書いたが、実際に名指しされていたのはタイとカンボジアのみ
- **パスポート残存期間は最終入国日起点** → 出発日起点で計算して1日ずれた
- **ドメインの乗っ取りに注意** → `cambodianembassy.jp` は2026年8月時点で大使館ではなく無関係のFXサイト。**リンクする前に必ず中身を開く**
- **空港のターミナル番号は実在を確認** → スワンナプーム(BKK)は**旅客ターミナルが1つだけでT1/T2は存在しない**。T1/T2があるのはドンムアン(DMK)
- **荷物スルーは航空会社の公式規定で判定** → ベトナム航空は「国際線→国際線・同一航空会社・乗継1ヶ所・5時間未満」なら最終目的地まで通し。現場の最終証拠は**バゲージタグに印字された空港コード**

### サイトが取れないとき
- **外務省・空港・航空会社サイトが403を返す**(Akamai) → 外務省は**モバイル版** `http://www.anzen.mofa.go.jp/m/` が iPhone の User-Agent + **Shift-JIS(cp932)デコード**で取得できる。国コード: カンボジア=004, タイ=007, ベトナム=015
- **ヘッドレスChromiumはネットワークに出られない**(proxy経由でもERR_CONNECTION_RESET) → 調査は curl/WebFetch/WebSearch、ブラウザは `file://` の表示確認専用

### 作業環境
- **GitHub Pages は main からのみデプロイできる**(`github-pages` 環境の保護ルール。作業ブランチからの実行は約1秒で失敗)
- **PR本文のHTMLタグはGitHubに消される**(`<select>` が消えた)→ 山括弧を使わず書く
- **アイコンPNGのスクショに白帯が入る**(Chromiumのスクショ領域がウィンドウより短い) → 512x700で撮ってPILで内容のバウンディングボックスから中央切り抜き
- **HTMLの一括置換はアサーションで守る**(置換前に出現回数を検査して、想定外なら止める)

## 禁止事項

- **推測で数字や行程を書くこと。** 「たぶんこうなるはず」で行程表を書かない
- 出典の無い断定(特に治安・料金・営業時間・法規)
- 政府公式以外の申請サイトへの誘導
- 1ソースだけで時刻・金額・営業時間を確定情報として載せること
- JavaScriptが無いと閲覧・タブ切り替えができない構造
- 外部リソースの読み込み
- ユーザーの個人情報の埋め込み(緊急メモ欄は空欄で用意する)
- **HTMLファイルそのものを納品物として渡すこと、Artifactで出すこと**(納品は共有URLのみ)
- **Service Workerの無いしおりを公開すること**(URLのみの納品ではオフラインの保証がSWしかない)
- 修正依頼で指定された範囲外を、確認なしに書き換えること
- ユーザーに対して専門用語で説明すること(コードが書けない前提)
